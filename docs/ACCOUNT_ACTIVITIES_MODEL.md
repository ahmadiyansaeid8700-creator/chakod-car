# مدل فعالیت‌های حساب چاکود

## تصمیم محصول
حساب کاربری چاکود یک هویت اصلی دارد و فعالیت‌های کسب‌وکاری به‌صورت مستقل به آن اضافه می‌شوند.

مدل «یک account_type که با تغییر آن نقش قبلی جایگزین شود» برای تجربه نهایی مناسب نیست.

هر فعالیت کسب‌وکاری یک «مجموعه» مستقل است و می‌تواند مالک و پرسنل خودش را داشته باشد. اعضای تیم با حساب شخصی خودشان وارد چاکود می‌شوند و هنگام کار، مجموعه‌ای را که از طرف آن فعالیت می‌کنند انتخاب می‌کنند.

## فعالیت‌های قابل افزودن
هر کاربر می‌تواند به‌عنوان مالک حداکثر یک مورد از هر نوع زیر داشته باشد:

- نمایشگاه خودرو (`dealer`)
- فروشگاه قطعات (`parts_store`)
- تعمیرگاه خودرو (`repair_shop`)
- مرکز خدمات خودرو (`car_service`)

بنابراین یک کاربر می‌تواند هم‌زمان چهار فعالیت متفاوت داشته باشد، اما نمی‌تواند دو نمایشگاه یا چند مورد از یک نوع ثبت کند.

این محدودیت فقط درباره مالکیت مستقیم کاربر است. یک کاربر می‌تواند هم‌زمان عضو تیم مجموعه‌های دیگر نیز باشد.

## تجربه حساب
در حساب کاربری بخشی با عنوان «فعالیت‌های من» نمایش داده می‌شود.

برای هر نوع:
- اگر هنوز ساخته نشده: دکمه «افزودن»
- اگر ساخته شده: کارت فعالیت + «مدیریت» + «حذف»
- دکمه افزودن همان نوع بعد از ایجاد دیگر نمایش داده نمی‌شود.

مجموعه‌هایی که کاربر مالک آن‌ها نیست اما عضو تیم آن‌هاست نیز باید در بخش جداگانه «مجموعه‌هایی که در آن‌ها فعالیت می‌کنم» نمایش داده شوند.

حذف باید واقعی و سمت Backend باشد و وابستگی‌های آن فعالیت (پروفایل عمومی، آگهی‌ها/خدمات مرتبط، وضعیت مالی، اعضای تیم و سایر داده‌ها) طبق سیاست حذف مدیریت شوند. حذف صرفاً با پنهان‌کردن Client مجاز نیست.

## تأیید مالک یا مدیر اصلی مجموعه
مالک یا مدیر اصلی مجموعه فقط با انتخاب یک نقش در UI تأیید نمی‌شود. برای اینکه چاکود یک کاربر را به‌عنوان مالک/نماینده مجاز یک کسب‌وکار بشناسد، مجموعه باید مرحله «تأیید مجموعه» را طی کند.

### مدارک
مدرک قابل قبول بسته به نوع فعالیت می‌تواند یکی از مدارک معتبر فعالیت مجموعه باشد؛ برای نمونه:
- پروانه کسب
- مجوز یا جواز فعالیت
- مدرک ثبتی مجموعه
- مدرک معتبر دیگری که ادمین برای آن نوع فعالیت تعریف کرده است

چاکود نباید فقط یک نوع مدرک ثابت را برای همه صنف‌ها اجباری کند؛ فهرست مدارک قابل قبول باید سمت Backend/Admin قابل تنظیم باشد.

اگر نام صاحب مدرک با شخص درخواست‌کننده متفاوت باشد، برای تأیید «مدیر/نماینده مجاز» باید مدرک تکمیلی ارتباط یا اختیار او نسبت به مجموعه نیز قابل دریافت باشد؛ مانند معرفی‌نامه یا مدرک نمایندگی معتبر. صرف داشتن شماره موبایل مجموعه برای اثبات مدیریت کافی نیست.

### وضعیت تأیید
هر activity حداقل یکی از وضعیت‌های زیر را دارد:
- `unverified`: مدرک هنوز ارسال نشده
- `pending`: مدرک ارسال شده و منتظر بررسی است
- `verified`: مالک/نماینده و مجموعه تأیید شده‌اند
- `rejected`: مدرک رد شده و دلیل قابل مشاهده برای درخواست‌کننده ثبت شده است
- `suspended`: تأیید یا دسترسی مجموعه موقتاً متوقف شده است

### رفتار سیستم
- کاربر می‌تواند قبل از تأیید، اطلاعات مجموعه را به‌صورت Draft تکمیل کند.
- نشان عمومی «تأییدشده» فقط بعد از `verified` نمایش داده می‌شود.
- دعوت پرسنل و اجرای تبلیغات از طرف مجموعه باید بعد از تأیید مجموعه فعال شود؛ این کار مانع ساخت تیم یا تبلیغ با نام یک کسب‌وکار جعلی می‌شود.
- پس از تأیید، مالک/مدیر تأییدشده می‌تواند پرسنل را دعوت کند. پرسنل برای عضویت عادی نیازی به بارگذاری پروانه کسب ندارند.
- پرسنل هویت و مجوز کاری خود را از membership همان activity می‌گیرند، نه از مدرک مالک.
- رد مدرک باید با `rejection_reason` همراه باشد تا کاربر بتواند مدرک اصلاح‌شده ارسال کند.

### محرمانگی مدارک
- تصویر/فایل مدرک عمومی نیست.
- پرسنل مجموعه به فایل مدرک دسترسی ندارند مگر permission ویژه و ضرورت مشخص وجود داشته باشد.
- فایل فقط برای فرایند بررسی ادمین و عملیات امنیتی مجاز قابل دسترسی است.
- URL خام یا مسیر ذخیره‌سازی مدرک نباید در API عمومی یا HTML عمومی افشا شود.
- دسترسی به فایل باید احراز هویت و مجوز سمت سرور داشته باشد.
- سیاست نگهداری و حذف مدارک باید قبل از Production مشخص شود و داده بیش از نیاز نگهداری نشود.

### حداقل قرارداد پیشنهادی تأیید
- `GET /api/account-activities/{id}/verification`
- `POST /api/account-activities/{id}/verification` برای ارسال درخواست و متادیتای مدرک
- Endpoint امن upload برای فایل مدرک
- Admin: مشاهده درخواست، فایل و سابقه بررسی
- Admin: `approve`, `reject`, `suspend`

حداقل داده پیشنهادی درخواست:
- `activity_id`
- `document_type`
- `document_reference` یا شماره مجوز در صورت وجود
- `license_holder_name`
- `applicant_relation` (`owner`, `manager`, `authorized_representative`)
- فایل اصلی مدرک
- فایل تکمیلی نمایندگی در صورت نیاز
- `status`
- `reviewed_by`
- `reviewed_at`
- `rejection_reason`

## تیم هر مجموعه
هر فعالیت یک تیم مستقل دارد.

مدل عضویت حداقل شامل این موارد است:
- `activity_id`
- `auth_user_id`
- نقش عضو
- وضعیت عضویت (`active`, `disabled`, `removed`)
- مجوزهای اضافه
- زمان ایجاد و آخرین تغییر

روی `(activity_id, auth_user_id)` باید uniqueness وجود داشته باشد تا یک کاربر دوبار عضو یک مجموعه نشود.

مالک مجموعه می‌تواند پرسنل را با شماره موبایل دعوت کند. عضو دعوت‌شده با همان حساب اصلی چاکود وارد می‌شود و حساب جداگانه سازمانی یا Login دوم ساخته نمی‌شود.

## قانون تبلیغات مجموعه
تمام اعضای فعال هر مجموعه به‌صورت پایه اجازه دارند برای همان مجموعه تبلیغ ایجاد و مدیریت کنند، مشروط به اینکه خود مجموعه در وضعیت `verified` باشد.

مجوز پایه:
- `ads.manage`

این مجوز برای عضو فعال اختیاری نیست و Backend نباید اجازه حذف آن را از عضو فعال بدهد. اگر عضویت `removed` شود، تمام دسترسی‌های مجموعه از جمله تبلیغات قطع می‌شوند.

امور مالی مستقل از مجوز تبلیغات است:
- مشاهده پرداخت‌ها: `payments.view`
- مدیریت پرداخت‌ها/کیف پول مجموعه: `payments.manage`

بنابراین پرسنل می‌توانند از طرف مجموعه کمپین و تبلیغ را مدیریت کنند، اما دسترسی به کیف پول، تسویه، بازپرداخت یا تنظیمات مالی فقط با مجوز مالی انجام می‌شود.

## نقش‌های پیشنهادی
- `owner`: مالک مجموعه و دسترسی کامل
- `manager`: مدیریت عملیاتی مجموعه
- `branch_manager`: مدیر شعبه در صورت اضافه‌شدن شعب
- `sales`: کارشناس فروش
- `content`: محتوا و تبلیغات
- `finance`: امور مالی
- `viewer`: مشاهده اطلاعات مجاز

`ads.manage` یک قابلیت پایه برای تمام اعضای فعال است و وابسته به عنوان نقش نیست، اما استفاده از آن برای یک مجموعه منوط به `verified` بودن خود activity است.

## اولین ورود
اولین ورود همچنان کوتاه است:
1. نام و نام خانوادگی
2. انتخاب نوع استفاده/فعالیت اولیه
3. در صورت انتخاب فعالیت کسب‌وکاری، حداقل اطلاعات لازم همان فعالیت
4. تکمیل راه‌اندازی و ورود به حساب

بارگذاری مدرک نباید Login اولیه را سنگین کند. اگر کاربر فعالیت کسب‌وکاری انتخاب کرد، بعد از ورود در «فعالیت‌های من» وضعیت «نیازمند تأیید مجموعه» نمایش داده می‌شود و فرایند ارسال مدرک از همان‌جا انجام می‌شود.

پس از راه‌اندازی اولیه، این صفحه دوباره نمایش داده نمی‌شود. فعالیت‌های دیگر فقط از «فعالیت‌های من» اضافه می‌شوند.

## محدودیت Backend فعلی
Frontend فعلی در بخش `professional-profile` هنوز پروفایل حرفه‌ای را به `user.account_type` واحد متصل می‌کند و یک پروفایل حرفه‌ای واحد فرض می‌کند.

Backend موجود نمایشگاه در `dealer-command-center` مفهوم اعضای تیم، نقش، permission و `ads.manage` را دارد. در لایه Next.js از این پس در دعوت و ویرایش عضو فعال، `ads.manage` به‌صورت اجباری به payload اضافه می‌شود تا تبلیغات برای عضو فعال قابل حذف نباشد.

برای اجرای کامل مدل روی همه انواع کسب‌وکار، Backend باید مفهوم عمومی `activity` را جایگزین وابستگی اختصاصی به dealer کند و collection مستقل فعالیت‌ها و اعضای آن‌ها داشته باشد، با uniqueness روی `(owner_user_id, activity_type)` برای مالکیت و `(activity_id, auth_user_id)` برای عضویت.

حداقل قرارداد پیشنهادی فعالیت‌ها:
- GET `/api/account-activities`
- POST `/api/account-activities` با `type`
- GET `/api/account-activities/{id}`
- PATCH/POST `/api/account-activities/{id}`
- DELETE `/api/account-activities/{id}`

حداقل قرارداد تیم:
- GET `/api/account-activities/{id}/members`
- POST `/api/account-activities/{id}/members`
- PATCH `/api/account-activities/{id}/members/{memberId}`
- DELETE یا تغییر وضعیت `/api/account-activities/{id}/members/{memberId}`

Backend باید ایجاد مورد دوم از یک type برای همان owner را رد کند و اجازه دسترسی هر عضو را فقط در context همان activity بررسی کند.

## قواعد
- یک هویت/ورود برای همه فعالیت‌ها و همه عضویت‌ها
- حداکثر یک فعالیت از هر type برای هر مالک
- امکان عضویت یک کاربر در چند مجموعه مستقل
- مالک/مدیر اصلی مجموعه بدون فرایند verification تأییدشده محسوب نمی‌شود
- permission و ownership فقط سمت Backend
- `ads.manage` برای تمام اعضای فعال هر مجموعه پایه و اجباری است، ولی تبلیغ از طرف مجموعه فقط پس از تأیید مجموعه فعال می‌شود
- دسترسی مالی جدا از تبلیغات است
- مدارک تأیید عمومی نیستند و باید با دسترسی سروری محافظت شوند
- حذف نیازمند تأیید صریح کاربر
- فعالیت دارای تعهد مالی/تسویه باز نباید بدون policy مشخص حذف شود
- UI نباید قابلیت چندفعالیتی را قبل از وجود قرارداد واقعی Backend جعل کند
