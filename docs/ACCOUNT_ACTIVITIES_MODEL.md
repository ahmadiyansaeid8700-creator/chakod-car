# مدل فعالیت‌های حساب چاکود

## تصمیم محصول
حساب کاربری چاکود یک هویت اصلی دارد و فعالیت‌های کسب‌وکاری به‌صورت مستقل به آن اضافه می‌شوند.

مدل «یک account_type که با تغییر آن نقش قبلی جایگزین شود» برای تجربه نهایی مناسب نیست.

## فعالیت‌های قابل افزودن
هر کاربر می‌تواند حداکثر یک مورد از هر نوع زیر داشته باشد:

- نمایشگاه خودرو (`dealer`)
- فروشگاه قطعات (`parts_store`)
- تعمیرگاه خودرو (`repair_shop`)
- مرکز خدمات خودرو (`car_service`)

بنابراین یک کاربر می‌تواند هم‌زمان چهار فعالیت متفاوت داشته باشد، اما نمی‌تواند دو نمایشگاه یا چند مورد از یک نوع ثبت کند.

## تجربه حساب
در حساب کاربری بخشی با عنوان «فعالیت‌های من» نمایش داده می‌شود.

برای هر نوع:
- اگر هنوز ساخته نشده: دکمه «افزودن»
- اگر ساخته شده: کارت فعالیت + «مدیریت» + «حذف»
- دکمه افزودن همان نوع بعد از ایجاد دیگر نمایش داده نمی‌شود.

حذف باید واقعی و سمت Backend باشد و وابستگی‌های آن فعالیت (پروفایل عمومی، آگهی‌ها/خدمات مرتبط، وضعیت مالی و سایر داده‌ها) طبق سیاست حذف مدیریت شوند. حذف صرفاً با پنهان‌کردن Client مجاز نیست.

## اولین ورود
اولین ورود همچنان کوتاه است:
1. نام و نام خانوادگی
2. انتخاب نوع استفاده/فعالیت اولیه
3. در صورت انتخاب فعالیت کسب‌وکاری، حداقل اطلاعات لازم همان فعالیت
4. تکمیل راه‌اندازی و ورود به حساب

پس از راه‌اندازی اولیه، این صفحه دوباره نمایش داده نمی‌شود. فعالیت‌های دیگر فقط از «فعالیت‌های من» اضافه می‌شوند.

## محدودیت Backend فعلی
Frontend فعلی در بخش `professional-profile` هنوز پروفایل حرفه‌ای را به `user.account_type` واحد متصل می‌کند و یک پروفایل حرفه‌ای واحد فرض می‌کند.

برای اجرای این مدل باید Backend یک collection مستقل از فعالیت‌های کاربر داشته باشد، با uniqueness روی `(user_id, activity_type)`.

حداقل قرارداد پیشنهادی:
- GET `/api/account-activities`
- POST `/api/account-activities` با `type`
- GET `/api/account-activities/{id}`
- PATCH/POST `/api/account-activities/{id}`
- DELETE `/api/account-activities/{id}`

Backend باید ایجاد مورد دوم از یک type برای همان user را رد کند.

## قواعد
- یک هویت/ورود برای همه فعالیت‌ها
- حداکثر یک فعالیت از هر type برای هر user
- permission و ownership فقط سمت Backend
- حذف نیازمند تأیید صریح کاربر
- فعالیت دارای تعهد مالی/تسویه باز نباید بدون policy مشخص حذف شود
- UI نباید قابلیت چندفعالیتی را قبل از وجود قرارداد واقعی Backend جعل کند
