# Chakod — Affiliate Request & Access Workflow

Status: APPROVED ARCHITECTURE / IMPLEMENTATION CONTRACT

این سند جریان درخواست، بررسی، تأیید و فعال‌سازی دسترسی افیلیت در چاکود را تعریف می‌کند. افیلیت یک `account_type` نیست؛ یک نقش/مجوز تکمیلی روی حساب موجود کاربر است.

## اصول قفل‌شده

- کاربر نمی‌تواند Affiliate را خودش فعال کند.
- فقط مدیر/ادمین مجاز می‌تواند درخواست را تأیید، رد، فعال، تعلیق یا غیرفعال کند.
- فرانت‌اند حق ندارد دسترسی افیلیت را از روی `account_type`، LocalStorage یا یک فلگ حدسی نتیجه‌گیری کند.
- نمایش Workspace افیلیت فقط بر اساس پاسخ صریح و معتبر بک‌اند انجام می‌شود.
- کنترل دسترسی درآمد، کمیسیون، تسویه و گزارش‌ها باید در بک‌اند enforce شود؛ مخفی‌کردن منوی UI کافی نیست.
- افیلیت مستقل از نوع حساب است؛ کاربر شخصی یا هر حساب کسب‌وکاری می‌تواند پس از تأیید مدیر نقش Affiliate داشته باشد.

## جایگاه در Account V2

### قبل از درخواست

در انتهای Account V2، داخل بخش کم‌اولویت «حساب و همکاری»، یک ورودی جمع‌شونده با عنوان «همکاری با چاکود» نمایش داده می‌شود.

این ورودی نباید در Hero، CTA اصلی یا دسترسی‌های سریع قرار بگیرد و نباید کاربر عادی را از وظیفه اصلی حساب منحرف کند.

CTA: `درخواست همکاری`

### بعد از ارسال درخواست

همان ورودی به یک Status Card کوچک تبدیل می‌شود و دیگر فرم جدید نمایش نمی‌دهد.

وضعیت نمونه:
- `در حال بررسی`
- `نیازمند تکمیل اطلاعات`
- `تأیید نشد`
- `تأیید شد — برای فعال‌شدن دسترسی دوباره وارد شوید`

### بعد از تأیید و ایجاد نشست جدید

ورودی «همکاری با چاکود» با Workspace واقعی `همکاری و درآمد` جایگزین می‌شود.

Workspace افیلیت شامل موارد زیر است:
- داشبورد خلاصه
- لینک/کد معرفی
- معرفی‌ها و وضعیت تبدیل
- کمیسیون در انتظار
- درآمد تأییدشده
- تسویه‌ها و تاریخچه پرداخت
- پروفایل تسویه
- قوانین و وضعیت دسترسی

## State Machine

Backend باید حداقل این وضعیت‌ها را پشتیبانی کند:

- `none`: کاربر درخواست فعال ندارد و Affiliate نیست.
- `draft`: درخواست شروع شده ولی ارسال نهایی نشده.
- `pending`: درخواست ارسال شده و منتظر بررسی مدیر است.
- `needs_info`: مدیر اطلاعات تکمیلی خواسته است.
- `approved`: درخواست تأیید شده ولی دسترسی در نشست جاری هنوز فعال نشده/نشست باید refresh شود.
- `active`: دسترسی Affiliate برای نشست کاربر فعال است.
- `rejected`: درخواست رد شده است.
- `suspended`: دسترسی Affiliate قبلی توسط مدیر متوقف شده است.
- `disabled`: نقش Affiliate توسط مدیر غیرفعال شده است.

فرانت‌اند باید تمام وضعیت‌ها را به‌صورت صریح هندل کند و برای حالت ناشناخته دسترسی را Fail Closed نگه دارد.

## فرم درخواست Affiliate

فرم Mobile First و مرحله‌ای باشد و در یک صفحه بلند نمایش داده نشود.

### مرحله ۱ — اطلاعات پایه

Prefill از حساب و فقط در صورت نیاز قابل اصلاح:
- نام و نام خانوادگی
- شماره موبایل تأییدشده
- شهر/استان
- روش تماس ترجیحی

### مرحله ۲ — زمینه همکاری

- کانال اصلی جذب/معرفی: شبکه اجتماعی، جامعه محلی، مشتریان کسب‌وکار، تولید محتوا، فروش، سایر
- لینک یا شناسه شبکه اجتماعی/وب‌سایت در صورت وجود
- حدود مخاطبان/جامعه هدف به‌صورت بازه، نه عدد اجباری دقیق
- سابقه کوتاه مرتبط
- توضیح کوتاه اینکه چرا قصد همکاری با چاکود را دارد

### مرحله ۳ — قوانین

کاربر باید نسخه مشخص قوانین Affiliate را ببیند و صریحاً تأیید کند.

Backend باید ذخیره کند:
- `terms_version`
- `accepted_at`
- شناسه کاربر
- در صورت نیاز audit metadata سمت سرور

### مرحله ۴ — بازبینی و ارسال

قبل از ارسال نهایی خلاصه اطلاعات نمایش داده شود.

پس از ارسال:
- درخواست immutable یا فقط با قواعد مشخص قابل ویرایش باشد.
- ارسال تکراری درخواست pending ممنوع شود.
- UI به Status Card تبدیل شود.

## اطلاعاتی که در درخواست اولیه نمی‌گیریم

برای کاهش PII و کوتاه‌شدن فرم، اطلاعات زیر قبل از تأیید دریافت نشوند:
- شماره شبا
- شماره کارت بانکی
- اطلاعات تسویه مالی غیرضروری

این اطلاعات فقط پس از Active شدن Affiliate و داخل «پروفایل تسویه» دریافت و اعتبارسنجی شوند.

## Admin Workflow

ساختار فعلی `/admin/users` مرجع اصلی هویت و وضعیت حساب کاربران است. مدیریت افیلیت باید با همین User ID یکپارچه شود.

پیشنهاد UI:
- در `/admin/users` برای کاربران دارای درخواست، Badge وضعیت Affiliate نمایش داده شود.
- یک فیلتر `درخواست افیلیت` اضافه شود.
- جزئیات درخواست در Drawer/صفحه جزئیات باز شود؛ نه اینکه همه فرم داخل کارت کاربر ریخته شود.
- در صورت زیادشدن حجم، مسیر `/admin/affiliate-requests` به‌عنوان Queue مدیریتی اضافه شود و از بخش «کاربران» قابل دسترسی باشد.

اکشن‌های مدیر:
- مشاهده درخواست و نسخه قوانین پذیرفته‌شده
- ثبت نتیجه تماس/پیام
- درخواست اطلاعات بیشتر
- تأیید
- رد + دلیل داخلی/نمایشی جدا
- فعال‌سازی نقش
- تعلیق/غیرفعال‌سازی نقش

همه تغییرات حساس باید در Audit Log ثبت شوند: actor admin، target user، action، timestamp و note.

## Approval & Session Refresh

پس از تأیید مدیر:

1. Backend نقش Affiliate را برای کاربر فعال می‌کند.
2. کاربر از طریق کانال تأییدشده (پیام/تماس و در صورت وجود پیام داخل سایت) مطلع می‌شود.
3. UI در نشست قدیمی فقط پیام `تأیید شد؛ برای فعال‌شدن امکانات یک‌بار خارج و دوباره وارد شوید` نشان می‌دهد.
4. پس از Logout/Login، نشست جدید باید Permission معتبر Affiliate را از سرور دریافت کند.
5. فقط پس از آن منوهای `همکاری و درآمد` نمایش داده شوند.

Logout/Login نباید تنها کنترل امنیتی باشد؛ Backend باید در هر Affiliate API مجوز نشست را بررسی کند.

## Permission Contract پیشنهادی

پاسخ session/me بهتر است نقش را به شکل explicit برگرداند، مثال مفهومی:

- `permissions.affiliate = true | false`
- `affiliate.status = none | draft | pending | needs_info | approved | active | rejected | suspended | disabled`

نام دقیق فیلدها باید با قرارداد واقعی Backend نهایی شود. فرانت نباید پیش از وجود قرارداد قطعی نام فیلد تولیدی را Hardcode و منتشر کند.

برای Admin یک Permission مستقل لازم است، مانند مفهوم `can_manage_affiliates`. صرفاً Admin بودن در UI نباید اجازه Mutation بدهد؛ Backend منبع حقیقت است.

## API Contract مورد نیاز Backend

نام endpointها نهایی نیست، اما قابلیت‌ها باید وجود داشته باشند:

User:
- دریافت status/request فعلی
- ایجاد/ذخیره draft
- ارسال نهایی درخواست
- ارسال اطلاعات تکمیلی پس از `needs_info`

Admin:
- فهرست/فیلتر درخواست‌ها
- دریافت جزئیات درخواست
- `request_more_info`
- `approve`
- `reject`
- `activate`
- `suspend`
- `disable`

Affiliate Active:
- summary
- referral code/link
- referrals/conversions
- commission ledger
- settlements
- payout profile

## Security Rules

- تمام Mutationها CSRF/cross-site protection مشابه مسیرهای مدیریتی فعلی داشته باشند.
- Authorization سمت سرور الزامی است.
- وضعیت Affiliate از LocalStorage قابل اعتماد نیست.
- کاربر فقط درخواست متعلق به User ID نشست خودش را می‌بیند/ویرایش می‌کند.
- Admin actions باید permission-checked و audit-logged باشند.
- هیچ مبلغ کمیسیون یا وضعیت تسویه صرفاً از داده client قابل تغییر نیست.
- درخواست pending نباید duplicate ایجاد کند.

## Blocker فعلی

Frontend موجود در این repository برای APIهای مدیریتی به `api.chakod.com` proxy می‌کند. سورس Backend `api.chakod.com` در repository متصل فعلی موجود نیست. بنابراین اجرای امن End-to-End Affiliate نیازمند اضافه‌شدن قرارداد/پیاده‌سازی Backend است؛ UI نباید قبل از آن دسترسی یا تأیید افیلیت را شبیه‌سازی کند.
