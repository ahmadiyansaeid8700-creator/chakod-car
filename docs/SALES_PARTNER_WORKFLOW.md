# Chakod — Sales Partner Workflow

Status: APPROVED PRODUCT DIRECTION / IMPLEMENTATION CONTRACT

این سند مدل «همکاری در فروش» حرفه‌ای چاکود را تعریف می‌کند. این مدل از «دعوت دوستان» عمومی جداست.

## تفکیک محصول

- «دعوت دوستان» برای همه کاربران است و پاداش غیرنقدی/اعتباری دارد.
- «همکاری در فروش» برای بازاریاب حرفه‌ای است و فقط بعد از بررسی و تأیید ادمین فعال می‌شود.
- هر دو از همان حساب و همان ورود چاکود استفاده می‌کنند؛ ورود جداگانه برای بازاریاب نداریم.

## ورودی از Account V2

در صفحه رسمی حساب یک گزینه واقعی با عنوان `همکاری در فروش` نمایش داده می‌شود.

اگر کاربر هنوز درخواست نداده باشد، با انتخاب این گزینه وارد صفحه درخواست همکاری می‌شود.

## فرم درخواست همکاری

فرم باید کوتاه، مرحله‌ای و Mobile First باشد.

### مرحله ۱ — اطلاعات هویتی و تماس

- نام و نام خانوادگی: ترجیحاً از پروفایل Prefill شود.
- شماره موبایل: از حساب کاربر گرفته شود و در حالت عادی قابل ویرایش نباشد.
- اگر شماره موبایل قبلاً در همین حساب تأیید شده، ارسال OTP جدید فقط برای درخواست همکاری الزامی نیست مگر سیاست امنیتی Backend آن را لازم بداند.

### مرحله ۲ — اطلاعات همکاری

حداقل اطلاعات لازم:
- روش اصلی بازاریابی/جذب مشتری
- لینک پیج/کانال/وب‌سایت در صورت وجود
- توضیح کوتاه درباره سابقه یا شبکه مشتری
- توضیح کوتاه درباره دلیل درخواست همکاری

### مرحله ۳ — قوانین همکاری

- کاربر نسخه مشخص قوانین همکاری در فروش را می‌بیند.
- باید صریحاً آن را تأیید کند.
- Backend باید `terms_version` و `accepted_at` و User ID را ثبت کند.

### مرحله ۴ — ارسال درخواست

پس از Submit:
- درخواست وارد وضعیت `pending` می‌شود.
- کاربر فقط Status Card می‌بیند و درخواست pending تکراری نمی‌سازد.
- ادمین درخواست را بررسی می‌کند.

## اطلاعات بانکی و شبا

شماره شبا در مرحله درخواست اولیه دریافت نشود.

دلیل:
- برای متقاضی ردشده PII بانکی غیرضروری ذخیره نمی‌کنیم.
- اطلاعات تسویه فقط زمانی لازم است که همکاری تأیید و فعال شده باشد.

پس از `approved/active`، کاربر در بخش `اطلاعات تسویه` شماره شبا را ثبت می‌کند.

Backend باید در صورت وجود سرویس معتبر احراز مالکیت، تطابق صاحب شبا با هویت صاحب حساب را بررسی کند. فرانت‌اند حق ندارد صرفاً از روی نام واردشده یا شماره موبایل مالکیت شبا را فرض کند.

## وضعیت‌ها

حداقل وضعیت‌های درخواست/دسترسی:
- `none`
- `pending`
- `needs_info`
- `approved`
- `active`
- `rejected`
- `suspended`
- `disabled`

حالت ناشناخته Fail Closed است.

## Admin Flow

ادمین باید بتواند:
- درخواست‌های pending را ببیند و فیلتر کند.
- جزئیات درخواست و قوانین پذیرفته‌شده را مشاهده کند.
- اطلاعات بیشتر درخواست کند.
- approve / reject انجام دهد.
- نقش همکاری در فروش را activate / suspend / disable کند.
- یادداشت داخلی بررسی ثبت کند.

تمام Mutationهای مدیریتی باید Audit Log داشته باشند.

## اطلاع‌رسانی تأیید

برای کاهش هزینه پیامک، تأیید همکاری به‌صورت پیش‌فرض از طریق سیستم داخلی چاکود انجام شود:

- یک تیکت/پیام سیستمی برای کاربر ایجاد شود.
- در Account V2 نیز اعلان وضعیت نمایش داده شود.

متن پیشنهادی:

`همکاری در فروش شما با موفقیت تأیید شد. برای فعال‌شدن امکانات همکاری، یک‌بار از حساب خود خارج شوید و دوباره وارد شوید. پس از ورود مجدد، بخش «فروش و درآمد» در حساب شما فعال خواهد شد.`

SMS برای این اعلان الزامی نیست. فقط اگر بعداً سیاست محصول یا امنیت نیاز داشت، می‌تواند به‌عنوان کانال تکمیلی استفاده شود.

## Session Refresh

پس از فعال‌سازی ادمین:
1. Backend Permission همکاری در فروش را برای User فعال می‌کند.
2. در نشست فعلی پیام تأیید نمایش داده می‌شود.
3. کاربر Logout/Login می‌کند.
4. نشست جدید Permission معتبر را از Backend دریافت می‌کند.
5. بخش `فروش و درآمد` نمایش داده می‌شود.

Logout/Login فقط برای Refresh تجربه کاربری است و مجوز واقعی باید در تمام APIهای همکاری سمت Backend بررسی شود.

## Workspace پس از فعال‌سازی

در نسخه اول صفحه بازاریاب فقط نیاز دارد:
- کد/لینک اختصاصی همکاری
- تعداد ورود/معرفی معتبر در صورت پشتیبانی Backend
- خریدهای موفق منتسب
- مبلغ فروش منتسب
- کمیسیون در انتظار
- کمیسیون تأییدشده
- اطلاعات تسویه
- تاریخچه تسویه
- قوانین و وضعیت حساب همکاری

## امنیت و حریم خصوصی

- Permission از LocalStorage قابل اعتماد نیست.
- درخواست/وضعیت باید به User ID نشست متصل باشد.
- اطلاعات بانکی فقط برای کاربر Active دریافت شود.
- اطلاعات هویتی مشتریان به بازاریاب نمایش داده نشود؛ فقط آمار و تراکنش‌های مجاز/تجمیعی.
- Self-referral و ثبت کمیسیون تکراری باید سمت Backend کنترل شود.
- Refund/Cancel باید روی کمیسیون اثر معکوس داشته باشد.

## Blocker فعلی

Frontend این repository به `api.chakod.com` متصل است، اما سورس Backend در repository متصل فعلی وجود ندارد. قبل از انتشار Flow واقعی درخواست/تأیید/تسویه، قرارداد و اجرای Backend باید اضافه یا تأیید شود.
